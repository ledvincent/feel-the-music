# Design

## Context

See proposal.md (Why). MOOD-2 left a Typer CLI where each command returns a result dict and `emit` prints it as JSON or text (`src/mood/cli.py`, design D2 and D3 of `openspec/changes/archive/mood-2-project-skeleton-2026-10-14/design.md`), and a frozen `Config` with the working folders (`src/mood/config.py`). `tests/test_cli.py` runs every registered command with `--json` in an empty temporary project, so `mood ingest --json` must print one JSON document there too.

This design follows `okf/architecture/overview.md` (modules `mood.ingest.split` and `mood.library`, `mood ingest` as the entry of the ingest flow), `okf/architecture/tech-stack.md` (TransNetV2 proposed for this ticket, PyAV allowed for frames, LanceDB pinned, models downloaded once from Hugging Face into `models/`), `okf/decisions/003-one-gpu-model-at-a-time.md` (passes load one model, free it, and are resumable), `okf/decisions/004-lancedb-one-row-per-shot.md` (Shot and Source tables, schema changes through `mood.library`, `pipeline_version`), `okf/decisions/007-keeper-clips-as-library.md` (sources stay where they are until keeper export) and the entity in `okf/data/shot.md`.

Code is written on a laptop without CUDA and run on the RTX 3060 Ti PC. Tests run on CPU, offline, with fake splitters and tiny videos generated at test time (no media committed).

## Goals / Non-Goals

**Goals:**
- A split pass and a library layer the later passes (MOOD-4 onwards) extend without rewriting: a splitter interface, a pass that loads one model and frees it, tables that gain columns by migration.
- Every outcome in the spec testable without a GPU, a network or a real TransNetV2.

**Non-Goals:**
- Any column beyond the ones listed in the proposal; moving files; deleting rows other than leftovers of an interrupted run; a progress bar.

## Decisions

**D1. Module layout.**
- `src/mood/library/` (`mood.library`): `schema.py` (Arrow schemas of Shot and Source, `PIPELINE_VERSION = 1`, `SCHEMA_VERSION = 1`), `store.py` (`Library`: open or create the LanceDB database in the `library` folder, look up a hash, write one file's rows, clean leftovers, run migrations).
- `src/mood/ingest/` : `inbox.py` (walk `inbox/`, sort files into videos and ignored, content hash), `split.py` (`mood.ingest.split`: the `Splitter` interface, TransNetV2 and PySceneDetect splitters, loading with fallback, cuts to shots), `run.py` (the ingest pass: skip, split, store, build the report).
- `src/mood/cli.py` gains `ingest`, which calls `run.ingest(config, splitter_factory)` and passes the result to `emit`; the exit code is 1 when any file failed, else 0. A text renderer prints one line per file and the totals.
Alternative: one `ingest.py` file; it would mix three concerns that later tickets extend separately (new passes in `mood.ingest`, new columns in `mood.library`).

**D2. Tables hold only this ticket's columns; later passes add theirs by migration.** Shot: `shot_id` (string), `source_file` (string, the path relative to `inbox/`, see D12), `source_hash` (string), `start_s`, `end_s`, `duration_s` (float64), `ingested_at` (timestamp, microseconds, UTC), `pipeline_version` (int32). Source: `source_hash` (string), `path` (string, absolute), `ingested_at` (timestamp UTC), `shot_count` (int32), `splitter` (string: `transnetv2` or `pyscenedetect`). `mood.library` keeps an ordered list of migrations, each a function from schema version N to N+1 (for example "add the cheap-pass columns, nullable"), and a small `meta` table holding the schema version; opening the library runs the missing ones. MOOD-4 adds its columns as migration 1→2 instead of editing this schema. Rows carry `pipeline_version`, so a pass can find rows it has not processed at the current version (decision 003). Alternative: reserve every column from `okf/data/shot.md` now as nulls; it fixes types (embedding size, tag lists) before the tickets that choose them, and an unused column hides whether a pass ran. Decision record needed: this extends decision 004 (how the schema grows); close-change records it in `okf/data/shot.md` and decision 004 or a new decision.

**D3. Content hash: SHA-256 of the whole file.** Streamed in 1 MiB chunks with `hashlib.sha256`, stored as lowercase hex in `source_hash`. It identifies the file by content, so a renamed copy has the same hash (spec "Renamed copy skipped"). The hash is computed for each video file before anything else; the skip check is one lookup in the Source table. Alternatives: hash of size plus the first and last few MB (much faster on films, but two different edits of the same film can collide); path plus modified time (a renamed copy would be ingested twice). Decision record needed: every Source and Shot row is keyed by this hash; changing the function later means rehashing every source.

**D4. Shot id: `<first 16 hex of source_hash>-<start in milliseconds, 9 digits>`.** For example `3fa4c1d09e2b7a65-000012480`. Deterministic, so a re-run of the same file after an interruption produces the same ids, and it stays readable in reel plans (`okf/data/reel-plan.md` references `shot_id`). Unique within a source because kept shots never share a start. Alternative: a random UUID per row; ids would change on every re-ingest and reel plans could not be re-created. Decision record needed: reel plans and the review page refer to shots by this id.

**D5. Splitter interface and cut-to-shot rules shared by both splitters.** `Splitter.split(path) -> SplitResult(duration_s, cuts_s)`, where `cuts_s` are the times (seconds, in the source) at which a new shot starts, ascending, without 0. One shared function turns that into shots: boundaries `[0, *cuts_s, duration_s]`, each shot the half-open span `[start_s, end_s)`, `duration_s = end_s - start_s`; a result with no cuts is one shot `[0, duration_s)` (spec "Video without cuts"); shots with `duration_s < 1.0` are dropped and counted (spec "Short shot dropped"; exactly 1.0 s is kept). Times are taken from frame timestamps (PTS × time base), not frame index ÷ frame rate, so variable-frame-rate phone videos get correct times; `duration_s` of the video is the end of its last frame. Fake splitters in tests return a `SplitResult` directly. A video shorter than 1 s with no cuts therefore has no kept shot: it is still ingested, with a Source row and `shot_count` 0, so it is not split again.

**D6. TransNetV2 in PyTorch, weights from Hugging Face.** TransNetV2 (Souček and Lokoč, MIT licence) scores every frame for a transition from 48×27 RGB thumbnails. The PyTorch model definition from the authors' repository is vendored as `src/mood/ingest/transnetv2_model.py` with its licence header (it is not on PyPI in a maintained form). Weights (`.pth`, about 30 MB) are fetched once with `huggingface_hub.hf_hub_download` into `models/transnetv2/`, from a repository and revision pinned in code (task 2.1 picks and pins it). Frames are decoded with PyAV (allowed in the tech stack), scaled to 48×27 in the decoder, and fed in the model's usual windows of 100 frames with 25 frames of context on each side, so memory stays flat for a two-hour film. A frame with transition score above 0.5 starts a new shot (the authors' default). Runs on CUDA in fp32 when available (the model is small, well under 1 GB of VRAM), else on CPU. Decision record needed: the splitter is a model choice (tech stack line); close-change writes `okf/decisions/010-transnetv2-shot-splitter.md` with this decision and the alternatives below, and updates the tech stack.
Alternatives considered for that record:
- PySceneDetect only: CPU, no model, but content thresholds miss soft cuts and fire on flashes and fast motion; kept as the fallback.
- AutoShot or other newer learned detectors: slightly better scores in papers, but weights and code are less packaged and less used.
- FFmpeg `scdet` / `select=gt(scene,…)`: no extra dependency, the weakest on dissolves and dark footage.

**D7. Fallback: PySceneDetect when TransNetV2 cannot be loaded.** `load_splitter(models_dir)` tries, in order: weights present in `models/transnetv2/`, else download them; then build the model and load the weights. Any failure in these steps (no network for the first download, missing or corrupt file, load error) returns the PySceneDetect splitter and a warning naming the reason, for example `TransNetV2 could not be loaded (weights not found and download failed: …); PySceneDetect split the videos instead`. The decision is made once per run, so one run uses one splitter, and the report's `splitter` field and every Source row of the run name it. PySceneDetect uses `ContentDetector` with its default threshold and the PyAV backend, on CPU; its scene list is turned into `cuts_s` (an empty list means no cuts, D5). A TransNetV2 that loads but runs on CPU is not a fallback (owner answer). Alternative: fall back per file; mixed splitters within one run would make the report harder to read for no gain.

**D8. One model for the batch, freed at the end of the pass.** The pass is: list and hash every video file; drop the skipped ones; if any file is left, load the splitter once, then for each file split and store it; at the end free the splitter. Loading and freeing are a context manager (`with load_splitter(...) as splitter:`), so the model is freed also when a file fails or the run is stopped with Ctrl+C. Freeing means dropping every reference to the model and its tensors, `gc.collect()` and `torch.cuda.empty_cache()`; the TransNetV2 module imports torch only when it is loaded, so `mood --help` stays fast. Storing a file's rows loads no model, so it happens right after that file is split: a stop loses at most the file in progress. When there is nothing to split (empty inbox, everything skipped) no splitter is loaded and the report's `splitter` is `null`. Spec "Splitter freed after split" is tested with a fake splitter that records `load`, each `split` and `free`, and asserts `free` is the last event, also when a split raises.

**D9. Source row last, as the commit marker; leftovers cleaned on open.** LanceDB commits each `add` to one table atomically but has no transaction across two tables. A file's kept Shot rows are written in one `add` to the Shot table, then its Source row in one `add` to the Source table. A file counts as ingested only when its Source row exists: the skip check reads the Source table only. When the library opens for an ingest run, Shot rows whose `source_hash` has no Source row (left by a stop between the two writes) are deleted, so the next run stores the file again without duplicates (spec "Interrupted file ingested again"). The test stops the run after the Shot write by making the Source write raise, then runs ingest again. Alternative: write the Source row first with a `complete` flag set later; needs an update step and a flag every later query would have to filter on.

**D10. Unreadable files.** Before splitting, the file is opened with PyAV and must have a video stream with frames; otherwise it fails with the reason (`cannot open: <PyAV message>`, `no video stream`). Decoding errors during the split (a truncated file) fail the file the same way, and so does any error raised by a splitter that loaded (for example TransNetV2 running out of GPU memory on one file): the run keeps that splitter for the other files, with no per-file fallback (owner answer; D7 decides the splitter once per run). A failed file gets no rows (its Shot rows are never written, D9), stays in `inbox/` (ingest never moves or deletes files in this ticket), and the run goes on with the next file; the exit code is 1 at the end. Hashing a file happens before opening it, so an unreadable file still shows its hash in the report.

**D11. Report shape.** One dict, rendered by `emit` (D3 of MOOD-2):
```
{"ok": bool, "inbox": "<path>", "nothing_to_ingest": bool,
 "splitter": "transnetv2" | "pyscenedetect" | null, "warnings": [str],
 "files": [{"file": "<path inside inbox, forward slashes>", "outcome": "ingested", "source_hash": str, "shots": int, "short_dropped": int}
         | {"file": ..., "outcome": "skipped", "source_hash": str, "reason": "already ingested"}
         | {"file": ..., "outcome": "failed", "reason": str}
         | {"file": ..., "outcome": "ignored"}],
 "totals": {"ingested": int, "skipped": int, "failed": int, "ignored": int, "shots": int, "short_dropped": int}}
```
`ok` is false when any file failed. Files are listed in path order. `nothing_to_ingest` is true when `inbox/` has no video file (only ignored files, or empty); the text output then says "Nothing to ingest in <inbox>".

**D12. Walking the inbox and naming files.** `inbox/` is walked recursively (`Path.rglob("*")`, files only, symbolic links not followed), so videos at any depth are ingested (spec "Video in subfolder ingested"). A video is a file whose lower-cased suffix is in the fixed tuple `.mp4 .mkv .mov .avi .webm .m4v`; every other file is listed as ignored and is never opened or hashed. Each file is named by its path relative to `inbox/`, with forward slashes (`films/amelie.mkv`): that is `source_file` on its Shot rows and `file` in the report, enough to find it in the inbox and stable across machines. Source `path` holds the absolute path, the field backlog 7 updates when the file moves to `processed/`. Identity stays the content hash (D3), so moving a file between subfolders does not re-ingest it. Alternative: `source_file` as the bare file name; two `clip.mp4` in different subfolders could not be told apart.

**D13. Missing inbox.** When the configured `inbox` folder does not exist, `mood ingest` raises `mood.config.ConfigError` before opening the library, with the message `inbox folder not found: <path>. Create it, or set folders.inbox in mood.toml.` The existing top-level handler in `cli.main` prints it as text, or as one `{"ok": false, "error": ...}` JSON document with `--json`, and exits 1 (spec "Missing inbox reported"). It also keeps `tests/test_cli.py::test_every_command_accepts_json` valid in an empty project: the output is one JSON document. The library folder is not created in that case.

**D14. Dependencies.** Add `lancedb` and `pyarrow`, `av`, `scenedetect` and `opencv-python-headless` (PySceneDetect's detectors use OpenCV; the headless build has no GUI libraries), `huggingface_hub`; pinned in `uv.lock`. All free and local; Hugging Face is used only for the one-time weights download, already listed as an external service in `okf/architecture/overview.md`.

## Risks / Trade-offs

- [No trustworthy Hugging Face repository with TransNetV2 PyTorch weights] → task 2.1 checks the candidates and the licence before coding the loader; if none fits, stop and ask the owner (converting the authors' TensorFlow weights once and hosting them in the owner's own Hugging Face repository is the likely answer). Until then the fallback keeps ingest working.
- [Hashing whole films every run: files stay in `inbox/` until backlog 7, so each run rehashes them, about 5 to 15 s for a 4 GB film on an SSD] → acceptable for an overnight tool; backlog 7 moves files out of the inbox. A cache keyed on path, size and modified time can come later if it hurts.
- [Frame-time precision: wrong times if frame index ÷ nominal fps were used on variable-frame-rate files] → D5 uses timestamps; a test checks shot times on a generated video with a known cut.
- [PySceneDetect and OpenCV wheels on Windows] → both publish Windows wheels for Python 3.12; checked by `uv sync` on the PC (task 1.1).
- [LanceDB API changes between versions] → pinned in `uv.lock`; all LanceDB calls stay inside `mood.library`.
- [`torch.cuda.empty_cache()` does not return memory still referenced] → the pass holds the model only inside the context manager; a manual check on the PC reads `torch.cuda.memory_allocated()` after the pass (task 5.3).

## Migration Plan

New tables, created on the first `mood ingest`; no existing data. Rollback is reverting the PR and deleting `library/` (git-ignored, regenerated by ingest).
